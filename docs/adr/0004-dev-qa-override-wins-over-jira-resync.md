# A Dev/QA Override always wins over Jira, once set

Every other cached field on a `Ticket` follows one rule throughout this spec: Jira is the source of truth, and a resync always overwrites the local copy with whatever Jira currently says. A `Dev/QA Override` breaks that rule on purpose — once a dev or qa Role assignment has been manually picked for a Split ticket, it keeps winning over that role's own `[Dev]`/`[Test]` Sub-task assignee even if Jira later grows one, or changes it. Resyncing a ticket never clears or supersedes its Override.

We considered letting a real, resolvable Sub-task assignee automatically supersede the Override once Jira catches up (self-healing back to "Jira is truth"). We rejected it because the Override exists specifically to answer a planning question Jira couldn't answer at the time — silently swapping the owner mid-sprint the next time someone clicks "Sync plan" would reshuffle a deliberate planning decision without anyone asking for that change, undermining the exact thing the Override was set up to stabilize. An Override is a Planning-only annotation, not a mirror of a Jira field, so it isn't held to the same "always reflects Jira" rule as the rest of `Ticket`. Reversing this later — making Jira data win again — would mean re-deriving which Overrides were ever actually meant as permanent picks vs. temporary stopgaps, information not captured today.
