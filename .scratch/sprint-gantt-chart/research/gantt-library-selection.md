# Gantt chart library selection — research findings

Scope: pick a JS/React Gantt library to build a **Sprint Planning Gantt** view in my-planner (`packages/frontend`, React 18/19 + TS + Vite). Research date: **2026-08-12**. This is desk research only — no packages installed, no application code written.

**Primary sources used**: each library's own npm registry JSON (`registry.npmjs.org`, `api.npmjs.org/downloads`), its GitHub repo (via `api.github.com` and raw file fetches — commit/release/license data), and its official documentation site. One vendor blog (SVAR's own comparison post) is cited only where explicitly flagged as vendor marketing, never as the sole source for a factual claim about a *competitor*. Every other claim below traces to a primary source linked inline.

---

## 0. What's actually driving the chart (read from this repo first)

Before evaluating libraries it's worth being precise about what data a Sprint Gantt would render, because it changes which library features actually matter:

- **`TeamSprintPlan`** (`packages/frontend/src/types.ts:326`) holds the sprint's own period: `startDate`/`endDate` (calendar-day strings) and `holidays: string[]` — a flat list of globally non-working dates within that period. `workingDays` is server-derived (`packages/backend/src/services/sprintWorkingDays.ts`), never client-computed.
- **`SprintCapacity`** (`types.ts:357`), returned by `GET /api/teams/:teamId/sprints/:sprintId/capacity` (`packages/backend/src/routes/capacity.ts:29`), gives each `TeamMembership` an `effectivePercentage` (allocation %), `extraHours`, and `leaveEntries: LeaveEntry[]` — each a `{date, portion: 'full'|'half'}` pair, already **server-reconciled** against the sprint's current working dates (`reconcileWithWorkingDates`, `capacity.ts:118`). `total`/`available`/`planned`/`remaining` are pre-computed **hours**, not calendar bars.
- **`SprintLeaveGrid.tsx`** is the existing UI for this: a plain HTML table, one row per person, one column per working day, cells click-cycled through none → half → full leave. It doesn't use any charting library — it's the thing a Gantt's "resource calendar" concept would need to visually agree with.
- **`SprintPlanEntry`** (`types.ts:267`) is the ordered ticket list: `order`/`devOrder`/`qaOrder` are three independent per-assignee rank namespaces; a Split (Story/Bug) ticket resolves to a `devQa: {dev, qa}` pair — **exactly** the "one Jira ticket, two rows (Dev bar, then QA bar)" scenario the Gantt needs to visually link.
- **Crucially, `Ticket` (`types.ts:216`) and `SprintPlanEntry` have no start/end date fields at all** — only `estimateHours` (and its planned/spill variants). There is no literal Jira due-date driving a bar's position. Bar start/end will have to be **computed by my-planner** (order + estimate hours + per-person available-hours-per-day), the same way `computeCapacity`/`plannedHours` already compute Planned/Remaining server-side. No Gantt library removes this work — it only needs to *render* already-computed bars.
- **`PlanningView.tsx`** already has a working row-reorder pattern: `@dnd-kit/core` + `@dnd-kit/sortable` (`SortableContext`, `arrayMove`, `useSortable` — see `PlanningView.tsx:2-3, 99-102, 692-798`), with a small drag-handle button (not the whole row) triggering a save-on-drop patch (`computeReorderPatches`, `PlanningView.tsx:99`). This is the app's established convention for "drag-reorder that persists an order field," and is a legitimate fallback mechanism if a chosen Gantt library can't do in-chart row drag itself.

This matters for the requirements below: because non-working days are already computed and reconciled **server-side**, a Gantt library doesn't strictly need a full auto-scheduling "working-time calendar engine" (which mainly exists to auto-*reschedule* dates around leave) — it needs to be able to **render pre-computed per-cell/per-row shading** for holidays/leave. That's a materially lower bar than what vendors gate behind "PRO resource calendars," though it still needs to be confirmed with a spike before committing (see §"What wasn't verified").

## 1. `frappe-gantt`

- **License**: MIT — confirmed in [npm registry metadata](https://registry.npmjs.org/frappe-gantt) (`"license": "MIT"`) and the [GitHub repo](https://github.com/frappe/gantt) (`license: MIT`, `6081` stars per [GitHub API](https://api.github.com/repos/frappe/gantt)).
- **npm package**: `frappe-gantt`. Latest `1.2.2`, published **2026-02-25** ([registry](https://registry.npmjs.org/frappe-gantt)). **139,522 downloads/week** ([npm downloads API](https://api.npmjs.org/downloads/point/last-week/frappe-gantt), week of 2026-08-03–09) — by far the most popular candidate evaluated.
- **Maintenance**: GitHub repo last pushed **2026-06-18**; most recent commits on default branch dated **2026-03-05** ([commits API](https://api.github.com/repos/frappe/gantt/commits)); 74 open issues ([repo API](https://api.github.com/repos/frappe/gantt)). Actively maintained, though note the last tagged GitHub *release* is `v1.0.3` (2025-02-03, per [releases/latest](https://api.github.com/repos/frappe/gantt/releases/latest)) while npm has since shipped `1.2.2` untagged — releases lag npm publishes here, a minor process smell but not a maintenance red flag on its own.
- **Bundle size**: unpacked npm package size **~244 KB** ([registry dist metadata](https://registry.npmjs.org/frappe-gantt)) — not the same as a minified+gzip browser bundle size, which I could not obtain (Bundlephobia's API 429'd repeatedly from this environment; flagged below as unverified).
- **React integration**: **none official**. The library exports a plain JS class that renders into a container element; the [README](https://github.com/frappe/gantt#readme) documents no React bindings. The community wrapper `frappe-gantt-react` on npm is essentially abandoned — latest `0.2.2` published **2019-05-03**, only **448 downloads/week** ([registry](https://registry.npmjs.org/frappe-gantt-react), [downloads](https://api.npmjs.org/downloads/point/last-week/frappe-gantt-react)) — not viable to depend on. Using frappe-gantt from React means hand-rolling a thin wrapper component (well-trodden pattern, but real work, and a hand-rolled wrapper needs its own re-render/diffing discipline against React's lifecycle).
- **Req 2 (resource/working-time calendar)**: **Partial.** The `holidays` config option supports marking dates non-working *globally* (`{date, label}` objects or a `'weekend'` keyword), per the [README](https://github.com/frappe/gantt#readme). There is **no per-resource/per-row calendar concept** — frappe-gantt has no notion of "this row belongs to person X, shade X's leave days differently from person Y's." Any per-row leave shading would have to be faked via custom bar/row styling hooks, not a first-class feature.
- **Req 3 (row reorder in-chart)**: **No.** The README documents dragging/resizing bars *along the timeline* and finish-to-start dependency arrows, but no drag-to-reorder-rows interaction or associated callback. Rows simply render in the order of the input array — reordering would have to happen *outside* frappe-gantt (e.g., feed it an array already reordered by the app's existing `@dnd-kit` pattern) rather than by dragging directly inside the Gantt UI, which is what the requirement explicitly asks for.
- **Req 4 (link/highlight same-ticket bars)**: **Partial/No.** Only generic finish-to-start dependency arrows via an `arrow_curve` parameter ([README](https://github.com/frappe/gantt#readme)); no documented per-link styling hook (no `id`-keyed class/color on an individual link) and no "shared id" grouping/coloring concept for two unrelated bars.

## 2. `gantt-task-react`

- **License**: MIT ([registry](https://registry.npmjs.org/gantt-task-react)).
- **npm package**: `gantt-task-react`. Latest `0.3.9`, published **2022-07-10** ([registry](https://registry.npmjs.org/gantt-task-react)). **62,034 downloads/week** ([downloads API](https://api.npmjs.org/downloads/point/last-week/gantt-task-react)).
- **Maintenance — disqualifying**: GitHub repo (`MaTeMaTuK/gantt-task-react`) last pushed **2024-08-12** — exactly **two years** before this research date, per [GitHub API](https://api.github.com/repos/MaTeMaTuK/gantt-task-react). 157 open issues, not archived but effectively dormant. Despite healthy download numbers (likely inertia from being an early "official-sounding" React Gantt), this is stale enough to rule out for new work in 2026.
- **React integration**: Yes, genuinely React-native (it *is* a React component library), per its [GitHub README](https://github.com/MaTeMaTuK/gantt-task-react#readme) — the one thing it does well.
- **Req 2**: **No** — no holiday/non-working-date or resource-calendar concept documented in the README.
- **Req 3**: **No** — no row drag-reorder feature or callback documented; only bar-level `onDateChange`/`onProgressChange`/`onSelect`/`onDoubleClick` callbacks.
- **Req 4**: **Partial** — `dependencies` is a plain array of parent task IDs per task (generic FS arrows), and each task supports a local `styles` override, but there's no documented per-*link* styling hook.
- **Verdict**: ruled out primarily on maintenance grounds regardless of feature fit.

## 3. `dhtmlx-gantt` (DHTMLX Gantt, Community + PRO)

- **License — notable recent change**: the Community Edition (npm package `dhtmlx-gantt`) is **MIT**, confirmed three ways: [npm registry](https://registry.npmjs.org/dhtmlx-gantt) (`"license": "MIT"`), [GitHub API license field](https://api.github.com/repos/DHTMLX/gantt) (`MIT`), and the repo's own [`LICENSE.md`](https://raw.githubusercontent.com/DHTMLX/gantt/master/LICENSE.md) (verbatim MIT text). This is a **recent relicense**: per DHTMLX's own [v10.0 announcement](https://dhtmlx.com/blog/dhtmlx-gantt-10-0/) and search-indexed docs, versions **9.x and earlier were GPL v2**; **v10+ switched the free edition to MIT**. Latest npm publish is `10.0.1` on **2026-08-04** ([registry](https://registry.npmjs.org/dhtmlx-gantt)) — i.e. this relicense is essentially current news relative to this research date.
- **npm package**: `dhtmlx-gantt`. **36,781 downloads/week** ([downloads API](https://api.npmjs.org/downloads/point/last-week/dhtmlx-gantt)).
- **Maintenance**: GitHub repo pushed **2026-08-04**, 1,831 stars, only **6 open issues** ([repo API](https://api.github.com/repos/DHTMLX/gantt)) — very actively maintained, low issue backlog (likely because paid support routes most issues off GitHub).
- **Bundle size**: unpacked npm size **~6.4 MB** ([registry dist metadata](https://registry.npmjs.org/dhtmlx-gantt)) — this is a large package (includes locales, styles, docs assets); actual gzip JS bundle size not independently verified (Bundlephobia unreachable, see below).
- **React integration — the key gap**: DHTMLX ships an official React wrapper, but it is **not free**. The npm package is literally named `@dhtmlx/trial-react-gantt` (latest `10.0.1`, [registry](https://registry.npmjs.org/@dhtmlx/trial-react-gantt)) and its own README states: `License: Evaluation` badge, and *"this npm package is a trial build intended for evaluation only... please request an evaluation on our website"* ([README, via registry](https://registry.npmjs.org/@dhtmlx/trial-react-gantt)). There is no separate free/MIT React wrapper package on npm — only `840`-ish weekly downloads on the trial package ([downloads API](https://api.npmjs.org/downloads/point/last-week/@dhtmlx/trial-react-gantt): 919/week) confirm it's a niche, evaluation-only artifact. Using the free Community core from React means hand-rolling a wrapper around a vanilla-JS class, same as frappe-gantt.
- **Req 2 (resource/working-time calendar)**: **No (Community) / Yes (PRO only)**. The [editions comparison page](https://docs.dhtmlx.com/gantt/guides/editions-comparison/) explicitly lists "Assigning Calendar to Project" and "Assigning Calendar to Resource" as PRO-only, and the [`resource_calendars` config docs](https://docs.dhtmlx.com/gantt/api/config/resource_calendars/) state outright: *"This functionality is available in the PRO edition only."* PRO pricing runs **$799–$5,999/year** across four tiers per search-indexed DHTMLX docs (not independently re-verified against a live pricing page in this pass).
- **Req 3 (row reorder in-chart)**: **Likely yes, edition unconfirmed.** `gantt.config.order_branch = true` plus the `onRowDragEnd(id, target)` event ([Reordering Tasks guide](https://docs.dhtmlx.com/gantt/guides/reordering-tasks/)) gives exactly a drag-to-reorder-rows interaction with a callback carrying the dragged id and its new neighbor. This wasn't listed under the PRO-only rows in the editions-comparison table I fetched (only "dragging *multiple* tasks horizontally" and "multi-task selection" were flagged PRO) — so single-row reorder is plausibly Community, but I did not find an explicit "Community: yes" statement to cite, so treat as needs-verification rather than confirmed.
- **Req 4 (link/highlight same-ticket bars)**: **Likely partial/yes, edition unconfirmed.** The `templates.link_class` hook lets you return a per-link CSS class based on the link's own data object ([`link_class` template docs](https://docs.dhtmlx.com/gantt/api/template/link_class/), [Links Coloring and Styling guide](https://docs.dhtmlx.com/gantt/guides/colouring-lines/)) — this is exactly the mechanism needed to highlight *one specific* Dev→QA link differently from all others (e.g. by keying off a shared ticket id embedded in the link object). Link objects have `id`/`source`/`target`/`type` plus `lag`/`readonly`/`editable` ([Link Properties docs](https://docs.dhtmlx.com/gantt/guides/link-properties/)) — nothing stops attaching an app-defined field the template reads. Edition tier of `link_class` itself wasn't explicitly stated in either doc page fetched.

## 4. SVAR React Gantt (`@svar-ui/react-gantt`)

- **License**: MIT for the open-source core — confirmed via [npm registry](https://registry.npmjs.org/@svar-ui/react-gantt) (`"license": "MIT"`) and [GitHub API](https://api.github.com/repos/svar-widgets/react-gantt) (`license: MIT`). A separate PRO evaluation package, `@svar-ui/trial-react-gantt`, exists with `license: "SEE LICENSE IN license.txt"` ([registry](https://registry.npmjs.org/@svar-ui/trial-react-gantt)) — mirroring DHTMLX's split, but critically **the free package here (`@svar-ui/react-gantt`) is the real, usable one**, not a crippled trial.
- **npm package**: `@svar-ui/react-gantt`. Latest `2.7.1`, published **2026-06-26** ([registry](https://registry.npmjs.org/@svar-ui/react-gantt)). **66,801 downloads/week** ([downloads API](https://api.npmjs.org/downloads/point/last-week/@svar-ui/react-gantt)) — smaller than frappe-gantt but comfortably ahead of gantt-task-react and dhtmlx-gantt.
- **Maintenance**: GitHub repo (`svar-widgets/react-gantt`) pushed **2026-06-29**, 200 stars, 14 open issues ([repo API](https://api.github.com/repos/svar-widgets/react-gantt)). Actively developed — spun out of the same team behind DHTMLX (per company background referenced in SVAR's own blog), now building a from-scratch React-native product line rather than wrapping the DHTMLX engine.
- **Bundle size**: unpacked npm package size **~928 KB** ([registry dist metadata](https://registry.npmjs.org/@svar-ui/react-gantt)) — again not a verified gzip browser-bundle figure.
- **React integration**: **Native.** Described directly (vendor claim, but structurally corroborated by it being a from-scratch npm React package rather than a `@dhtmlx`-style wrapper-around-vanilla-JS) as *"native React integration (no wrappers around legacy code)"* in [SVAR's own comparison post](https://svar.dev/blog/top-react-gantt-charts/) — flagged as vendor marketing, but the underlying fact (it ships as a real React component package, TypeScript-typed, React 19-compatible) is independently supported by the npm package itself being importable React components rather than a DOM-mounting class.
- **Req 2 (resource/working-time calendar)**: **No (open-source) / Yes (PRO only)** — same pattern as DHTMLX. The [pricing/feature comparison](https://svar.dev/react/gantt/pricing/) lists "Individual calendars for tasks" and "Individual calendars for resources" as PRO-exclusive; the [SVAR Gantt 2.7 release post](https://svar.dev/blog/svar-gantt-2-7-with-resource-planning/) (announcing exactly this resource-planning feature set) confirms resource assignment, resource load visualization, and individual work calendars are all **PRO-only**, while the free edition's 2.7 additions were virtual scale rendering, tooltips, and Excel/CSV import.
- **Req 3 (row reorder in-chart)**: **Yes, in the open-source edition.** The [pricing comparison](https://svar.dev/react/gantt/pricing/) explicitly lists "Dragging tasks to reorder" under both editions ("Both versions support 'Dragging tasks to reorder'"). The underlying mechanism is a `drag-task` action on SVAR's action-bus API, interceptable via `api.intercept("drag-task", ...)` per SVAR's own docs (surfaced via web search of `docs.svar.dev`, not independently re-fetched as a full page in this pass — flagged below) — which gives a hook to persist the new order, matching this app's existing "save-on-drop" pattern in `PlanningView.tsx`.
- **Req 4 (link/highlight same-ticket bars)**: **Partial, same as DHTMLX.** Dependency links are a free/open-source feature (`type: "s2s"|"s2e"|"e2s"|"e2e"`, per the [links API reference](https://docs.svar.dev/react/gantt/api/properties/links/)), and links carry `id`/`source`/`target`/`type`/`lag`. I could not find a documented per-link `cssClass`/color field in the fetched API reference — but because this is a real React component (not a DOM-templated vanilla-JS engine like DHTMLX), a custom link-rendering override is a much more natural fit for React's component-override patterns than for DHTMLX's template-string hooks. Treat as **needs a short spike**, not a confirmed "no."

## 5. `bryntum-gantt` (Bryntum Gantt + React wrapper)

- **License**: fully commercial, no free/open-source tier. [Bryntum's own licensing page](https://bryntum.com/products/gantt/license/) describes only paid **End-User** (perpetual, for internal apps) and **OEM** (for redistributed/SaaS products) licenses, explicitly stating *"every developer who has access to or works with Bryntum code or components must have their own unique license."* SVAR's comparison blog independently cites pricing *"starts from $940 per developer"* ([source](https://svar.dev/blog/top-react-gantt-charts/), vendor-of-a-competitor citing a price — treat as directionally correct, not gospel).
- **npm packages**: `@bryntum/gantt` (core) and `@bryntum/gantt-react` (wrapper) both exist on the registry, latest `7.3.4` ([registry](https://registry.npmjs.org/@bryntum/gantt-react)), but with only **124–128 downloads/week** each ([downloads API](https://api.npmjs.org/downloads/point/last-week/@bryntum/gantt-react)) — consistent with a package that's typically installed from a private/licensed registry rather than public npm by most real users, so these public-npm numbers understate actual usage.
- **React integration**: official wrapper package exists (`@bryntum/gantt-react`).
- **Reqs 2/3/4**: almost certainly the strongest of any candidate here (Bryntum's commercial Gantt is generally considered feature-complete for resource calendars, drag-reorder, and dependency styling) — but this was **not independently verified against requirements 2–4** given the "ruled out on license" decision below; not worth spending further research budget confirming feature depth on a product this project's license preference already excludes.
- **Verdict**: ruled out immediately on the explicit "free/OSS strongly preferred" requirement — ruled out primarily on license/cost.

## 6. `vis-timeline`

- **License**: dual **`(Apache-2.0 OR MIT)`** per [npm registry](https://registry.npmjs.org/vis-timeline) — genuinely permissive (GitHub's license-detector shows "Other/NOASSERTION" only because it can't parse a dual-license SPDX expression, per [GitHub API](https://api.github.com/repos/visjs/vis-timeline); the npm-declared SPDX is authoritative here).
- **npm package**: `vis-timeline`. Latest `8.5.3`, published **2026-08-05** ([registry](https://registry.npmjs.org/vis-timeline)). **257,052 downloads/week** ([downloads API](https://api.npmjs.org/downloads/point/last-week/vis-timeline)) — the highest raw download count of any candidate, though this reflects its broader use as a general timeline visualizer, not Gantt-specific adoption.
- **Maintenance**: GitHub repo pushed **2026-08-05**, 2,540 stars, 300 open issues ([repo API](https://api.github.com/repos/visjs/vis-timeline)) — actively maintained but with a heavier issue backlog than the Gantt-specific libraries above.
- **React integration**: none official — renders into a container div, same vanilla-JS-wrapper situation as frappe-gantt/dhtmlx-gantt Community.
- **Req 2**: not evaluated in depth — moot given req 4 below.
- **Req 3 (row/group reorder)**: **Yes, partial.** Groups (rows) can be drag-reordered via `groupEditable.order: true`, with a `groupDragged` event firing after drop — though the event only passes the dragged group's id, not a ready-made new-order list, and a `groupOrderSwap` function must be supplied by the app ([vis-timeline Groups docs](https://visjs.github.io/vis-timeline/docs/timeline/#Groups)). Workable, but more app-side wiring than the Gantt-specific libraries' single order-index callback.
- **Req 4 (dependency links) — disqualifying**: **No.** vis-timeline's own docs make **no mention of dependency arrows, task linking, or relationship visualization between items** at all ([vis-timeline docs](https://visjs.github.io/vis-timeline/docs/timeline/#Groups)) — it's a timeline/calendar visualizer (items on a time axis, optionally grouped into rows), not a Gantt engine with a dependency model. Per this task's own instruction not to force-fit a library that can't do dependencies, **vis-timeline is ruled out** despite its size/license appeal — there is no built-in or documented-plugin path to the Dev→QA link-highlighting requirement.

## 7. Ruled out quickly, with reasons

- **`gantt-schedule-timeline-calendar` (GSTC)**: license is a custom **"NEURONET Free/Trial"** license, not a standard OSS license — free use requires the *consuming application's own source code* to be public under MIT/ISC ([LICENSE file](https://github.com/neuronetio/gantt-schedule-timeline-calendar/blob/master/LICENSE)), which my-planner (a private repo) doesn't satisfy; commercial/private use gets a **2-month trial** before requiring a paid license. Combined with low adoption (**4,400 downloads/week**, [downloads API](https://api.npmjs.org/downloads/point/last-week/gantt-schedule-timeline-calendar)), not worth further evaluation.
- **`frappe-gantt-react`**: covered under frappe-gantt above — effectively abandoned (2019, 448/week), not a viable React path.

## What wasn't / couldn't be verified

- **Real gzip bundle sizes.** Bundlephobia's API returned `429 Too Many Requests` on every attempt from this environment (both `bundlephobia.com/api/size` and repeated retries with backoff). The unpacked npm-package sizes cited above (from registry `dist.unpackedSize`) are a poor proxy — they include source maps, docs, locale files, etc., not just the browser-loaded JS. Get real numbers from `bundlephobia.com` directly (or `npx bundle-phobia <pkg>` if such a CLI is available) before committing.
- **Whether `dhtmlx-gantt`'s `order_branch`/`onRowDragEnd` row-reorder and `templates.link_class` per-link styling are Community-tier or silently PRO-gated.** The editions-comparison page I fetched didn't list either as PRO-only, but I also couldn't find an explicit "yes, Community" statement for either — DHTMLX's docs split PRO-gating notices unevenly across many pages. Worth a 15-minute spike against the actual free npm package before ruling dhtmlx-gantt in or out on this basis.
- **SVAR React Gantt's exact API for reading the new row order after a `drag-task` reorder**, and whether a link object supports a custom/`cssClass`-style field for single-link highlighting. Both surfaced only via search snippets referencing `docs.svar.dev` pages that 404'd when fetched directly in this pass (SVAR's docs site structure seems to have moved some pages recently, consistent with the fast 2.x release cadence). Needs a direct doc-site crawl or a quick spike against the real package.
- **Bryntum Gantt's actual feature depth on reqs 2–4** — not investigated beyond confirming its commercial-only licensing, since license alone rules it out for this project. If the license constraint is ever relaxed, it's worth a real look; Bryntum is generally the most feature-complete option in this space by reputation.
- **Anything about a live rendering/visual quality comparison** — no screenshots, demos, or hands-on trials were done; this is desk research from docs/metadata only, per the task's constraints.
- **Whether "per-resource day shading without a built-in calendar engine" is actually achievable in SVAR's or frappe-gantt's free tier** — the reasoning in §0 (that pre-computed leave/holiday data only needs *rendering*, not a scheduling engine) is my inference from this repo's architecture, not something confirmed against either library's customization API. This is the single most important thing to prototype before committing — it's the crux of whether the PRO-gated "resource calendar" gap actually matters for my-planner.

## Recommendation

**Primary pick: SVAR React Gantt, open-source edition (`@svar-ui/react-gantt`).**

Reasoning, tied to the stated priorities:

1. **Req 1 (React integration) — it wins outright.** It's the only candidate that is both genuinely native React (not a hand-wrapped vanilla-JS class) *and* actively maintained (npm publish 2026-06-26, GitHub push 2026-06-29) *and* free. `gantt-task-react` matches "official React" but is two years stale — a real risk for a library you'll be extending (row-reorder callbacks, custom link rendering) rather than using off the shelf. `dhtmlx-gantt`'s official React wrapper is commercial-only in practice (`@dhtmlx/trial-react-gantt`, "Evaluation" license). frappe-gantt has no React binding at all.
2. **Req 3 (row reorder in-chart) — the only library that confirms this in its free tier.** SVAR's pricing page explicitly lists drag-to-reorder as available in *both* editions, with a `drag-task` action on its API bus to hook persistence — a good match for this app's existing save-on-drop pattern (`computeReorderPatches` in `PlanningView.tsx`). frappe-gantt and gantt-task-react don't have this at all; dhtmlx-gantt's equivalent (`onRowDragEnd`) exists but its Community-tier status is unconfirmed.
3. **Req 2 (resource calendar) — the PRO gap is real but not disqualifying, given §0.** SVAR (like DHTMLX) reserves per-resource/individual calendars for PRO. But my-planner already computes and reconciles leave/holidays server-side (`sprintWorkingDays.ts`, `leaveEntries.ts`) — the Gantt view only needs to *render* that pre-computed data (shade specific cells per row), not run its own scheduling engine. That's a custom-rendering problem, which a true React component (SVAR) is structurally better positioned to solve cleanly than a template-string-based vanilla engine (frappe-gantt/dhtmlx). This needs a short spike to confirm before committing (see above), but it's the right bet given the rest of the scorecard.
4. **Req 4 (link highlighting) — genuinely unresolved everywhere, SVAR included.** No candidate documents a clean single-link highlight/shared-id-grouping API. This is the one area where SVAR's advantage is inferred (React component overrides are generally more tractable than DOM-template hooks) rather than confirmed, and it should be the first thing prototyped once the library is installed.
5. **License/maintenance**: MIT, current, actively developed, with a paid upgrade path (PRO) available later if the resource-calendar gap turns out to matter more than expected — a reasonable hedge for a personal project that doesn't want to be stuck if requirements grow.

**Fallback pick: `frappe-gantt`.**

If SVAR's newer/smaller ecosystem (200 GitHub stars vs. frappe-gantt's 6,081; a vendor clearly optimizing its docs to upsell PRO) causes friction in practice — API instability, thin docs, or the link-highlighting spike coming back genuinely infeasible — frappe-gantt is the safe fallback: the most popular (139k/week), most battle-tested, most actively committed-to (near-weekly commits through March 2026) MIT library evaluated, with the smallest footprint. Its two real gaps are both directly patchable using this repo's own existing patterns rather than needing new infrastructure:

- **No React binding** → hand-roll a thin wrapper component (a well-understood pattern; frappe-gantt's constructor-and-refresh API is simple enough that this is low-risk).
- **No in-chart row drag-reorder** → don't fight it; reuse the app's existing `@dnd-kit`-based sortable pattern from `PlanningView.tsx` as a *separate* reorder affordance (e.g. a compact sortable ticket list alongside the chart) that feeds an already-ordered array into frappe-gantt on each change, rather than expecting the Gantt itself to own the drag interaction. This sidesteps req 3 as a chart feature entirely by satisfying it at the app layer instead — consistent with how this app already handles ticket ordering everywhere else.

**Ruled out, not reconsidered**: `bryntum-gantt` (commercial-only, contradicts the free/OSS requirement for a personal project), `vis-timeline` (no dependency-link support at all — a hard requirement, not force-fittable), `gantt-task-react` (stale — no commit in 2 years), `gantt-schedule-timeline-calendar` (non-standard license incompatible with a private repo).
