# 01 — SVAR Gantt feasibility prototype

Type: prototype
Status: resolved

## Question

Build a throwaway `@svar-ui/react-gantt` (open-source edition) prototype, driven by real shapes from this app's data (`TeamSprintPlan`, `SprintCapacity`, `SprintPlanEntry`), to answer:

1. Can per-row leave/holiday shading be rendered using **pre-computed** data (from the existing capacity endpoint) without needing SVAR's PRO-gated resource-calendar feature? (The research's working theory in `.scratch/sprint-gantt-chart/research/gantt-library-selection.md` §0 is that this only needs *rendering*, not a scheduling engine — confirm or refute.)
2. Can a Split ticket's Dev bar and QA bar — which may land on **different people's rows** — be visually linked or highlighted as belonging to the same ticket? This is a **hard v1 requirement** (see the map's Decided section), and the research flagged it as unresolved in every library evaluated, SVAR included. If SVAR genuinely cannot do this cleanly, this ticket must decide the fallback (e.g. `frappe-gantt` + hand-rolled link rendering, reconsidering `dhtmlx-gantt` Community's `link_class` hook, or another approach) rather than deferring the question further down the map.
3. Does dragging a bar to a new start date work in practice, and can the app read back the resulting new date (to persist as a start-date override) and the resulting new row order (to write back to `order`/`devOrder`/`qaOrder`)?
4. What should the popup/modal container look like at "larger" size holding this chart — is there an existing modal component/convention in this codebase to reuse (check `docs/ui-conventions.md` first)?

If the SVAR pick is confirmed, note any API specifics discovered (e.g. exact prop/hook names for shading, linking, drag events) so later tickets can rely on them. If SVAR is rejected, record the replacement pick and why, updating the map's Notes section accordingly.

## Answer

**SVAR React Gantt (open-source, `@svar-ui/react-gantt@2.7.1`) is confirmed viable for all four questions.** No fallback needed — stick with the primary pick from the research doc.

Prototype: built and driven with fixture data shaped like `TeamSprintPlan`/`SprintCapacity`/`SprintPlanEntry` (3 people, a rough walk-forward placement, a Split ticket with Dev on one person's row and QA on another's), wired behind a real "Gantt chart" button in `PlanningView.tsx`'s "Tickets by person" header (before `SyncPlanButton`, per the map's grounding fact), opening a modal. Verified interactively via chrome-devtools (DOM inspection + synthetic drag) against the actual running app. Captured on branch `prototype/sprint-gantt-svar-feasibility` (commit `627734c`) — not on `main`.

**1. Per-row leave/holiday shading without PRO — confirmed, via a different mechanism than assumed.** SVAR's `highlightTime` config hook (the one free-tier "shading" hook in the type defs) is **global/per-column only** — `(date, unit) => string`, no row/resource argument — so it can't do per-person shading on its own. Instead: render each leave/holiday day as an ordinary **sibling task** under the person's row (1-day duration, styled via CSS — see API specifics below). This uses only core/free hierarchical tasks, needs zero PRO features, and composes for free with the map's existing "overlapping bars allowed" decision (leave bars and ticket bars on the same row just overlap visually, exactly like `SprintLeaveGrid`'s cells). Colors reused exactly: full leave/holiday = `#f87171`/`#ef4444` border (Tailwind red-400/500), half leave = `#fcd34d`/`#f59e0b` border (amber-300/500).

**2. Dev/QA bar linking across different people's rows — confirmed, two independent mechanisms, both working:**
   - **Native dependency link**: SVAR's `links` config (core/free — dependency links are NOT in the PRO list) with `type: 's2s'` between the Dev task id and QA task id renders an actual connector line (elbow polyline with arrowhead) between the two bars, even when they're in non-adjacent rows belonging to different people. Confirmed by inspecting the rendered SVG (`<g class="wx-line">` with a polyline spanning both rows' y-coordinates).
   - **Matching color/border via CSS**: every rendered bar carries a `data-id` attribute set to the task's own id, verbatim (confirmed via DOM inspection: `<div class="wx-bar" data-id=":dev-PROJ-201">`). Giving the Dev and QA placements deterministic, related ids (e.g. `dev-<jiraKey>` / `qa-<jiraKey>`) and targeting them with a plain `<style>` block (`[data-id^=":dev-"]`, `[data-id^=":qa-"]`) gives them a shared background/border with zero dependency on any undocumented per-link styling API. This is more robust than what the research flagged as unresolved (`link_class`-style hooks) — it doesn't touch links at all.
   - Both were verified simultaneously in the live prototype: PROJ-201 [Dev] (Bob's row) and PROJ-201 [QA] (Carol's row) render in matching violet with a dashed-vs-solid yellow border, connected by a visible elbow line.

**3. Drag-to-reschedule — confirmed, both readback and row-order derivation are straightforward.** Dragging a bar's body updates the task's `start`/`end` and fires an `update-task` event (prop name `onUpdateTask` if passed as a React prop; also subscribable via `api.on('update-task', cb)` from the `init` prop, which is what the prototype used). Inside that handler, `api.getTask(id)` returns the new `start`/`end` as `Date` objects — directly usable as the persisted start-date override. Verified live: a synthetic mousedown/mousemove/mouseup sequence on the PROJ-101 bar moved it from Aug 10 to Aug 13–15, and the app read back `{id: "entry-PROJ-101", start: "2026-08-13", end: "2026-08-15"}` correctly.
   "New row order" is **not** something the library computes or needs to — the map's "time-axis-only drag" decision means row membership never changes, so the "new order" question reduces to: after a drag, compare the moved ticket's new start date against its row-siblings' start dates and re-derive `order`/`devOrder`/`qaOrder` from the sort. Plain app-level logic, not a library concern. (Note for Ticket 05: SVAR's core install doesn't include row-*reorder*-by-dragging in the tree/resource sense used here, since "rows" are synthetic parent tasks, not SVAR resources — see API specifics below.)

**4. Modal container — a widened variant of `docs/ui-conventions.md` Archetype B (full modal dialog), not a new archetype.** The base archetype's `max-w-sm` is far too narrow for a multi-week timeline; the prototype used `max-w-6xl` (backdrop/card/border/shadow classes otherwise unchanged) plus `max-h-[90vh] overflow-hidden` on the card with `overflow-auto` on the inner content — the base archetype has no height cap since its dialogs are always short. Recommend the real implementation ticket capture this as a documented "large modal" variant in `docs/ui-conventions.md` rather than reinventing the width/height numbers later.

**API specifics for later tickets:**
- **Rows-as-people, without PRO "resource planning"**: SVAR's readme explicitly lists "Task grouping" and "Resource planning" under the **PRO** feature list (not previously known to the research doc, which only flagged the resource-*calendar* as PRO). The workaround used here — and recommended for the real implementation — is to **not use SVAR's resource/grouping features at all**. Instead, build a synthetic task tree: one parent `task` per person (`id: "person-<personId>"`, `parent: 0`, spanning the sprint dates), with each ticket placement and leave/holiday day as a `parent`-linked child. This is core/free hierarchical tasks (`data`/`parent` on `ITask`), fully sufficient for "one row per person," and sidesteps the PRO gate entirely. The person's own summary bar is hidden via `[data-id^=":person-"] { visibility: hidden }` so only the row label shows in the grid pane.
- **Custom `type` values do NOT get their own CSS class.** The compiled bundle maps a bar's class via `wx-${type}`, but only recognizes `task`/`summary`/`milestone` (or ids matching registered `taskTypes`) — any other string collapses to the default `wx-task` class. Use `data-id` for custom per-bar styling hooks instead (see Q2 above), not `type`.
- **Drag events are plain DOM `mousedown`/`mousemove`/`mouseup`** (not Pointer Events) attached via a React synthetic handler on the `.wx-bars` container (mousedown/mousemove) plus a `window` listener for mouseup. A ~5–20px move threshold gates when a click becomes a drag.
- Package: `@svar-ui/react-gantt@2.7.1` + `import '@svar-ui/react-gantt/all.css'`; wrap in `<WillowDark>` for this app's dark theme (also re-exports `Willow` for light mode, though the app doesn't currently need to switch Gantt theme with the app's own light/dark toggle — worth a follow-up check, not blocking).
- Columns/grid pane: `columns={[{ id: 'text', header: 'Row', flexgrow: 1 }]}` gives the simple "Row" label column seen in the prototype; a real implementation will likely want this narrower or hidden in favor of the app's own left-hand labels.

**Not covered by this ticket** (left to Tickets 02–06, unaffected by anything found here): the real placement algorithm, one-cursor-per-person-vs-per-role, unassigned-ticket handling, and the persistence/reconciliation model.
