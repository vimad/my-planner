# 24 — Dev/QA split: Planning view dual-row display + assignment popup

**What to build:** The frontend half of the Dev/QA split — a Story/Bug's ticket badge appears under both its resolved dev owner's row and its resolved qa owner's row in "Tickets by person" (ticket 18), a flagged "needs dev/qa" indicator for whichever role isn't resolved yet, and the popup that lets you fill in or edit a `TicketDevQaOverride`. Demoable: add a story with a real `[Dev]`/`[Test]` sub-task split — see it land under both people's rows; add one with no sub-tasks — the add-to-plan popup opens immediately asking who's doing dev and who's doing qa. See `.scratch/sprint-jira-integration/spec.md` ("Planning view UI"), [CONTEXT.md](../../../CONTEXT.md) ("Split ticket", "Role assignment", "Dev/QA Override"). Resolved via a `/grill-with-docs` session — see that conversation for the full decision tree.

**Blocked by:** 18 — Planning view: capacity strip + ticket table; 23 — Dev/QA split: Override model + role resolution + capacity API.

**Status:** ready-for-human

- [x] "Tickets by person" table: a Split ticket (Story/Bug) renders its badge once under the resolved dev person's row and once under the resolved qa person's row (same ticket key), each badge carrying a small "DEV"/"QA" sub-label alongside the existing type sub-label so the two placements are distinguishable at a glance. Non-split tickets keep today's single-row placement, unchanged.
- [x] A role that resolves to `needs-assignment` (ticket 23) renders as a distinct flagged badge — visually separate from the existing amber Unmapped treatment, which stays exactly as-is for a real-but-off-roster Sub-task assignee — clickable to open the assignment popup for that ticket.
- [x] `DevQaAssignmentPopup`: shows both roles for the ticket. A role currently resolved from a real Sub-task renders read-only (labeled "from Jira", no edit affordance). A role that's `needs-assignment` or already carries a `TicketDevQaOverride` renders an editable `<select>` over the team roster; saving calls ticket 23's `PUT /api/tickets/:ticketId/dev-qa-override`.
- [x] The popup is reachable two ways: (1) automatically, right after `AddToPlanForm`'s submit succeeds, if the newly-added ticket is a Split ticket with either role unresolved — skippable, closing it without picking still leaves the ticket in the plan, flagged for later; (2) by clicking any "needs dev/qa" flagged badge anywhere in the table (covers `Sync plan`-discovered and pre-existing unresolved tickets, no auto-interrupt outside the add-to-plan flow) — same popup, pre-filled with current resolution either way.
- [x] Frontend tests cover: a Split ticket's badge appearing in both the dev and qa rows with correct sub-labels, a "needs dev/qa" flagged badge opening the popup on click and saving an override that moves the badge into the picked person's row, the add-to-plan flow auto-opening the popup only when a role is unresolved (and not at all for a fully-resolved or non-split ticket), and a resolved-via-Jira role rendering read-only in the popup.

## Comments

Implemented per spec. No backend changes were needed — ticket 23's API contract was consumed as-is.

**What was built:**
- `packages/frontend/src/types.ts` — added `DevQaRoleResolution` (mirrors `services/devQaResolution.ts`'s union exactly, not imported cross-package) and extended `SprintPlanEntry` with `devOrder: number | null`, `qaOrder: number | null`, and optional `devQa?: { dev: DevQaRoleResolution; qa: DevQaRoleResolution }`.
- `packages/frontend/src/components/PlanningView.tsx`:
  - New `PlacedEntry` type (`{ entry: SprintPlanEntry; role?: 'dev' | 'qa' }`) — a ticket's single placement within one person's row. A Split entry contributes up to two `PlacedEntry` values (one per role), a non-split entry exactly one.
  - `TicketBadge` gained `role`, `needsAssignment`, and `onFlagClick` props. `role` renders the "DEV"/"QA" sub-label. `needsAssignment` renders the badge as a `<button>` (not a `<span>`) in the new sky-blue "flag" styling and wires `onFlagClick`.
  - `PersonRow` now takes `placements: PlacedEntry[]` and a `variant: 'normal' | 'unmapped' | 'needsAssignment'` (was a single `unmapped` boolean) — `variant` drives the row's label/empty-state color uniformly; `unmapped` styling is byte-for-byte unchanged from before (verified: the pre-existing "flagged unmapped row" test needed zero changes).
  - The grouping `useMemo` (renamed outputs `ticketsByMembershipId` / `unmappedPlacements` / `needsAssignmentPlacements`) branches on `entry.devQa` presence (not `ticket.type` — per ticket 23's contract, this is the correct discriminator): a non-split entry keeps the exact original assigneeAccountId-based placement; a Split entry resolves each role independently into a per-membership bucket (matched by resolved `personId`, not `jiraAccountId`), the `unmapped` bucket, or the new `needsAssignment` bucket. A resolved role whose `personId` no longer matches any current `TeamMembership` (e.g. an Override pointing at someone since removed from the team) falls back to the `unmapped` bucket rather than silently vanishing — a defensive edge case beyond the literal checklist.
  - A third table row, "Needs dev/qa" (❓ prefix, sky-colored), was added below "Unmapped" (⚠, amber, unchanged) to host `needsAssignment`-variant placements — this row didn't exist before; it's where a `needs-assignment` role's flagged badge actually lives (the checklist didn't pin down which row this badge renders in, only that it must be visually distinct from Unmapped, so I added a dedicated bucket rather than trying to wedge it into an existing one).
  - New state: `popupTicketId` (which ticket's popup, if any, is open) and `pendingAutoOpenTicketId` (a just-added ticket's id, watched via a `useEffect` keyed on `entries` until it reappears devQa-decorated post-refresh, at which point the popup auto-opens only if `dev.status === 'needs-assignment' || qa.status === 'needs-assignment'` — `unmapped` deliberately does not auto-open, per the ticket text's explicit call-out).
- `packages/frontend/src/components/DevQaAssignmentPopup.tsx` (new file, not inlined into `PlanningView.tsx`) — modeled directly on `ConfirmDialog.tsx`'s archetype-B full modal (`docs/ui-conventions.md`). Put in its own file rather than inline, matching this repo's existing convention that every modal (`ConfirmDialog.tsx`, `BoardSwitcherModal.tsx`, etc.) is its own component file. Each role renders via an internal `RoleField`: read-only (a plain div, no edit control) when `status === 'resolved' && source === 'subtask'`; an editable `<select>` over `memberships` otherwise (`needs-assignment`, `unmapped`, or `resolved`+`source: 'override'`), pre-filled to the current `personId` when resolved. A `RoleHint` line under each field explains the status in words (off-roster Jira assignee vs. no sub-task found yet vs. manually assigned) using the existing amber tone for the unmapped hint and the new sky tone for the needs-assignment hint. On submit, only fields whose value actually changed from their initial resolution are included in the PUT body (an untouched, already-correct Override is never re-sent); if nothing changed, `Save` just closes. The popup only closes itself on a successful save (or explicit Close/Cancel) — a failed save keeps it open with the user's picks intact and shows the error inline.
- `packages/frontend/src/hooks/useSprintPlan.ts` — `addTicket` now returns the created `SprintPlanEntry` (parses the POST response body, previously discarded) so `PlanningView` can identify which ticket to watch for; added `saveDevQaOverride(ticketId, body)` (+ `savingDevQaOverride`/`devQaOverrideError` state) calling `PUT /api/tickets/:ticketId/dev-qa-override` then `refreshPlan()`, following this hook's existing per-action loading/error state pattern exactly.
- `docs/ui-conventions.md` — added a "needs attention, click to resolve" flag entry under Semantic colors: `border-sky-300 bg-sky-100 text-sky-700 dark:border-sky-500/30 dark:bg-sky-500/20 dark:text-sky-300`, reserving sky for this one meaning (distinct from amber Unmapped, red/rose destructive, cyan office-linked, emerald completed). The convention doc didn't have a pre-existing color for this specific "clickable prompt to fill in missing data" semantic, so this is a deliberate, documented deviation per the doc's own "if you deviate, deviate on purpose and update this doc" instruction.

**Deviations from a literal reading of the checklist (all called out above too, repeated here for visibility):**
1. No backend changes were made or needed — the POST `/api/sprint-plan-entries` response still isn't `devQa`-decorated (only GET is, per ticket 23). The auto-open flow works around this by watching `entries` (GET-sourced) for the newly-added ticket to reappear, rather than reading `devQa` off the POST response directly.
2. Added a dedicated "Needs dev/qa" table row that wasn't explicitly specified — the checklist required the flagged badge to be "visually separate from Unmapped" but didn't say which row hosts it.
3. A resolved role whose person has left the roster falls back into the Unmapped bucket (not in the checklist, added defensively so a ticket can never silently disappear from the table).

**Flaky-test investigation — root-caused and fixed, not left as a rabbit hole:**
The pre-existing flake ticket 23 flagged ("PlanningView.test.tsx, 2 tests, only when run as part of the full suite — passes in isolation") turned out to be broader than that description: stress-testing (10-15 repeated runs) found it also fails **in isolation**, at a lower but still material rate, and affects a *third* test beyond the two ticket 23 saw. Root cause in all cases was the same pattern: asserting on a `waitFor`-resolved condition proves only one of two independently-resolving fetches (sprints/memberships vs. capacity+entries, both fired from separate `useEffect`s in `useSprintPlan.ts`) has settled, then immediately (synchronously, no wait) asserting on state that depends on the *other* fetch. Two concrete instances:
- `getByText('100')`/`getByText('150')` right after `waitFor`ing only on the row's `aria-label` (row renders once memberships load; the ticket badge inside it renders once entries load — independently timed). Fixed by waiting on the badge text itself (`findByLabelText` + a `waitFor`-wrapped inner assertion), not just the row.
- `getByText('Ada Lovelace')` right after render, in "renders capacity cards with the API-computed numbers" — this text is ambiguous between the CapacityCard (gated on the capacity fetch) and the "Tickets for Ada Lovelace" row's own label (gated on the independent memberships fetch); `waitFor` could resolve via the row appearing first. Fixed by waiting on `'32h planned'` instead, a CapacityCard-only string with exactly one source.
One of my own new tests (the needs-assignment flagged-badge test) hit the same class of race during authoring and was fixed the same way before it ever reached this report.
Verification: 35 consecutive full-suite (`pnpm --filter frontend test`) runs and 15 consecutive isolated-file runs, all green, after the fixes above (previously failing at roughly a third to half of runs). Not a rabbit hole in the end — same one-line-fix pattern repeated three times, not a structural issue in the app code.
