# 23 — Dev/QA split: Override model + role resolution + capacity API

**What to build:** The backend half of splitting a Story/Bug's Planning-view placement into two independently-tracked roles (dev, qa) instead of one shared assignee — the `TicketDevQaOverride` model, the role-resolution logic, the endpoint to set an override, and the capacity/Planned math update that goes with it. See `.scratch/sprint-jira-integration/spec.md` ("Domain model", "Planning view UI"), [CONTEXT.md](../../../CONTEXT.md) ("Split ticket", "Role assignment", "Dev/QA Override"), and [ADR 0004](../../../docs/adr/0004-dev-qa-override-wins-over-jira-resync.md). Resolved via a `/grill-with-docs` session — see that conversation for the full decision tree (why every Story/Bug always splits, why an Override outlives resync, why Planned never invents a per-role estimate).

**Blocked by:** 12 — Team, Person & TeamMembership: models + CRUD API; 13 — Sprint, Ticket, Epic & SprintPlanEntry: models + Full sync + Planning API; 14 — Capacity: models + formula + API.

**Status:** ready-for-human

- [x] `packages/backend/src/models/TicketDevQaOverride.ts`: `ticketId` (ref `Ticket`, unique), `devPersonId: ObjectId | null` (ref `Person`), `qaPersonId: ObjectId | null` (ref `Person`). Global per ticket — not scoped to team or sprint — and stored in its own collection so `fullSyncTickets`'s upserts never touch it (this separation is what makes ADR 0004's "Override always wins, resync never resets it" true for free).
- [x] `packages/backend/src/models/SprintPlanEntry.ts`: add `devOrder: number | null` and `qaOrder: number | null`. A Split ticket (Story/Bug) uses these instead of the existing `order`; a non-split ticket (Task/Sub-task/anything else) keeps using plain `order`, unchanged from ticket 13/10's behavior.
- [x] A role-resolution helper (e.g. `packages/backend/src/services/devQaResolution.ts`) — given a Story/Bug `Ticket` and the team's current `TeamMembership` list, resolves dev and qa independently, in order: (1) `TicketDevQaOverride` if set for that role, (2) a real `[Dev]`/`[Test]` child Sub-task (via `parentKey` + `subtaskKind`) whose `assigneeAccountId` matches a membership, (3) a real child Sub-task whose assignee doesn't match any membership → `unmapped`, (4) no real Sub-task of that kind, or it's unassigned, and no Override → `needs-assignment`. Returns each role's status plus enough to render it (`resolved` → personId; `unmapped` → the raw assignee display fields already on `Ticket`; `needs-assignment` → nothing else). Non-Story/Bug tickets never call this — they keep today's single-`assigneeAccountId` grouping entirely.
- [x] `GET /api/sprint-plan-entries?teamId=&sprintId=` includes each Split entry's resolved dev/qa role status inline, so the frontend doesn't re-derive Sub-task/Override lookups itself.
- [x] `PUT /api/tickets/:ticketId/dev-qa-override` — body `{ devPersonId?: string | null, qaPersonId?: string | null }`, upserts the `TicketDevQaOverride` (only the provided fields change). Used by ticket 24's popup, both for filling in a `needs-assignment` role and for later editing an already-overridden role.
- [x] `routes/capacity.ts`'s Planned computation: for a Split ticket, the dev person's Planned only counts that ticket's `[Dev]` Sub-task's own `estimateHours` (0 if none exists), and the qa person's Planned only counts the `[Test]` Sub-task's own `estimateHours` (0 if none) — never a share of the parent ticket's own `estimateHours`. Non-split tickets keep today's `computeEffortHours` roll-up attributed to the parent's single `assigneeAccountId`, unchanged.
- [x] `routes/sprintPlanEntries.ts`'s `applyReassignmentResets`: for a Split ticket, a role's real Sub-task assignee changing resets that role's own `devOrder`/`qaOrder` (mirroring today's single-`order` reset) — but only when that role isn't currently pinned by a `TicketDevQaOverride` (an overridden role never moves on resync, per ADR 0004). Non-split tickets keep today's behavior on plain `order`.
- [x] Backend tests cover: role resolution's four states (override / mapped sub-task / unmapped / needs-assignment) resolved independently for dev and for qa; an Override surviving a resync that changes the ticket's or its sub-tasks' cached data; Planned correctly summing per-role sub-task estimates (including the 0-hour cases); and `devOrder`/`qaOrder` behaving like today's `order` (reset on real reassignment, untouched by `TeamMembership` changes) while a non-split ticket's plain `order` is unaffected by any of this.

## Comments

Implemented per spec, plus two additions and one deliberate gap — details below.

**What was built:**
- `packages/backend/src/models/TicketDevQaOverride.ts` — new collection, `{ ticketId (unique), devPersonId, qaPersonId }`.
- `packages/backend/src/models/SprintPlanEntry.ts` — added `devOrder: number | null`, `qaOrder: number | null` (schema default `null`).
- `packages/backend/src/services/devQaResolution.ts` — `isSplitTicket(type)`, `resolveDevQa(ticket, memberships)` (the 4-state precedence chain), `roleSubtaskEstimateHours(jiraKey, kind)` (Planned's per-role figure).
- `packages/backend/src/routes/tickets.ts` (new router, mounted at `/api/tickets` in `app.ts`) — `PUT /api/tickets/:ticketId/dev-qa-override`.
- `packages/backend/src/routes/sprintPlanEntries.ts` — GET now inlines `devQa` on Split entries; POST seeds `devOrder`/`qaOrder` on creation (see deviation below); `applyReassignmentResets` gained a new `applyDevQaRoleResets` pass plus a `nextOrderForRole` helper (the per-role analogue of `nextOrderForAssignee`).
- `routes/capacity.ts` — Planned computation now branches: Split-ticket entries are resolved once per ticket (not per person) into a `personId -> hours` map via `resolveDevQa` + `roleSubtaskEstimateHours`, non-split entries keep the exact original `assigneeAccountId`/`computeEffortHours` path, now explicitly filtered to `!isSplitTicket(...)`.

**Exact `GET /api/sprint-plan-entries` response shape ticket 24 depends on:** each entry keeps its existing fields untouched (`_id, teamId, sprintId, ticketId, addedAt, order, devOrder, qaOrder`); a Split entry (ticket.type `'Story'`/`'Bug'`) additionally carries a top-level `devQa: { dev: DevQaRoleResolution, qa: DevQaRoleResolution }` key. `DevQaRoleResolution` (exported from `services/devQaResolution.ts`) is a discriminated union on `status`:
- `{ status: 'resolved', source: 'override' | 'subtask', personId: string }` — `source` is what lets ticket 24 tell a Jira-sourced role (read-only) apart from an Override (editable).
- `{ status: 'unmapped', assigneeAccountId, assigneeDisplayName, assigneeEmail }` — same raw display fields `Ticket` already caches.
- `{ status: 'needs-assignment' }` — nothing else.
A non-split entry has no `devQa` key at all (not `null` — omitted), so existing/simple consumers don't need to branch on it.

**Two additions beyond the literal checklist** (needed for the feature to actually work end-to-end; called out explicitly since they weren't in the checklist text):
1. **`devOrder`/`qaOrder` seeding on `POST /api/sprint-plan-entries`.** The checklist only asked for `applyReassignmentResets` to *reset* these fields on a later resync, but a brand-new Split ticket has no prior `SprintPlanEntry` for that reset path to touch (it runs before the entry exists). Without seeding, every newly-added Split ticket would sit at `devOrder: null, qaOrder: null` forever unless a resync happened to change a sub-task assignee afterward. Added: right after creating the entry, if the ticket is Split, resolve dev/qa immediately and seed whichever role(s) already resolve via a new `nextOrderForRole` helper (mirrors `nextOrderForAssignee`); a role that's `needs-assignment`/`unmapped` at creation time is simply omitted from the create payload (stays `null` via the schema default) until it resolves later.
2. **`applyDevQaRoleResets` is keyed off a synced *Sub-task's* own assignee change**, not the parent's, and is deliberately **not gated on `isNew`** the way the original non-split loop is — a brand-new `[Dev]`/`[Test]` sub-task appearing on a ticket that was already in the plan (previously `needs-assignment`) needs to seed `devOrder`/`qaOrder` too, not just a reassignment of a pre-existing sub-task. Also excluded Split tickets entirely from the *original* `order`-reset loop (their own `assigneeAccountId`, if Jira even sets one, is irrelevant to Planning-view placement now).

**One deliberate gap, flagged for ticket 24:** `PATCH /api/sprint-plan-entries/:id` still only accepts `{ order }` — it was not extended to accept `devOrder`/`qaOrder`. The checklist didn't call for it, and I didn't want to guess at ticket 24's drag-reorder contract. Ticket 24's implementer will need to either extend this PATCH endpoint (adding optional `devOrder`/`qaOrder` body fields, same "only touch what's present" convention used elsewhere in this repo) or add a dedicated one before wiring up dev/qa row drag-reorder.

**Testing:** followed this repo's actual convention (vi.mock'd Mongoose models + supertest against `createApp()` — there is no mongodb-memory-server anywhere in this repo despite the ticket text's mention of it; copied boilerplate from `capacity.route.test.ts` / `sprintPlanEntries.route.test.ts` as instructed). New/extended files: `test/devQaResolution.test.ts` (all 4 resolution states, independent dev/qa resolution on one ticket, Override-survives-resync, `roleSubtaskEstimateHours` 0-hour cases), `test/tickets.route.test.ts` (PUT upsert, partial-field semantics, explicit-null-clears), `test/capacity.route.test.ts` (3 new tests under a `Split ticket (Story/Bug) Planned` block), `test/sprintPlanEntries.route.test.ts` (GET inline `devQa` + non-split-unaffected, POST seeding + non-split-unaffected, sync-triggered `devOrder` reset with `qaOrder` pinned-by-Override left untouched, and a no-change no-op test). All existing tests needed zero modification — non-split behavior is bit-for-bit unchanged (verified: `SprintPlanEntry.create`'s call payload for a non-split ticket is byte-identical to before, since `devOrder`/`qaOrder` keys are only added to the payload when the ticket is Split).
