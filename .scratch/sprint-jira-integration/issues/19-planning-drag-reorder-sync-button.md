# 19 — Planning: drag-reorder + "Sync plan" button

**What to build:** Per-row drag-and-drop reordering of ticket badges, persisted, plus the global full-resync action — the two remaining interactive pieces of the Planning table from ticket 18. Demoable: drag a badge to a new position within a person's row and reload — the order sticks; click "Sync plan" and see every ticket's data (and staleness) refresh. See `.scratch/sprint-jira-integration/spec.md` ("Planning view UI", ticket 10's resolution).

**Blocked by:** 13 — Sprint, Ticket, Epic & SprintPlanEntry: models + Full sync + Planning API; 18 — Planning view: capacity strip + ticket table; 23 — Dev/QA split: Override model + role resolution + capacity API.

**Status:** ready-for-human

## Comments

Implemented per spec, plus one addition needed to close a gap ticket 23 flagged for this ticket.

**What was built:**
- `packages/backend/src/routes/sprintPlanEntries.ts` — `PATCH /api/sprint-plan-entries/:id` extended from `{ order }`-only to `{ order?, devOrder?, qaOrder? }`, only-touch-what's-present (same convention as `PUT /api/tickets/:ticketId/dev-qa-override`). This was ticket 23's explicitly-flagged deliberate gap ("Ticket 24's implementer will need to either extend this PATCH endpoint... or add a dedicated one") — extended the existing endpoint rather than adding a new one, since the shape ticket 23 anticipated (optional per-field body) was the natural fit.
- `packages/frontend/src/hooks/useSprintPlan.ts` — `reorderEntries(patches)`: optimistic local patch of `entries` state, one `PATCH` per changed field, rolling every patch in the drop back to its pre-drag value if any fails (mirrors `TodoDetail.tsx`'s linked-todo reorder). `syncPlan()`: `POST /api/sprint-plan-entries/sync` then `refreshPlan()` (re-fetches capacity+entries together, same convention as every other plan-mutating action in this hook), with `syncingPlan`/`syncPlanError` state.
- `packages/frontend/src/components/PlanningView.tsx` — `SortableTicketBadge` (small separate drag-handle button + `TicketBadge`, mirroring `SortableBoardCard`/`SortableLinkedTodoRow`); `PersonRow` gained an `onReorder` prop and its own `DndContext`/`SortableContext` per row (real per-membership rows only — see deviation below); `computeReorderPatches(placements, oldIndex, newIndex)` renumbers each of the three independent order namespaces (`order`/`devOrder`/`qaOrder`) by its own position among only its own group after the drag, returning patches only for entries whose field value actually changed. `SyncPlanButton` added next to the "Tickets by person" heading.

**One scope decision beyond the literal checklist:** drag-reorder is wired up only for real per-person rows (`PersonRow`'s `variant='normal'`), not the Unmapped/Needs dev/qa catch-all rows. Unmapped can contain placements from several *different* real Jira assignees (SprintPlanEntry's `order` is meaningful only relative to entries sharing the *same* assignee — see the model comment); reordering across them would write `order` values that don't correspond to a real per-assignee group and could carry stale meaning if that assignee later joins the team. The ticket's own demoable description ("drag a badge to a new position within a person's row") and every other reference to this feature scope it to actual person rows, so this reads as an intentional boundary rather than a gap — flagging it here in case that's wrong.

**Testing:** `test/sprintPlanEntries.route.test.ts` gained 4 new PATCH cases (devOrder-only, qaOrder-only, non-numeric rejection for both, empty-body rejection). `PlanningView.test.tsx` gained two `vi.mock`s (`@dnd-kit/core`'s `DndContext` captured per-row by mount-order index via `useRef`, since this view — unlike `BoardsView`/`TodoDetail` — mounts one independent `DndContext` per row; `@dnd-kit/sortable`'s `SortableContext`/`useSortable` stubbed) plus two new `describe` blocks: "Drag-reorder" (cross-position reorder + PATCH + reload-persistence; no-op same-position drop; Split ticket's own-role-only patching using a same-entry dual-role fixture, since two placements in *different* order-namespaces don't actually generate a patch when swapped — needed two placements sharing one namespace to exercise the real invariant; optimistic-rollback-on-failure) and "Sync plan" (loading state via a deferred fetch promise, since the default stub resolves near-instantly; staleness/`lastSyncedAt` display refresh; error state; reassigned-ticket row move).
