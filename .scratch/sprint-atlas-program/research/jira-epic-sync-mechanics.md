# Jira epic/task sync mechanics — research findings

Resolves: `.scratch/sprint-atlas-program/issues/01-jira-epic-sync-mechanics.md`
Scope: `wealthos.atlassian.net`, project `WOSMVP`. Goal: pin down the concrete Jira API surface Atlas's own (brand-new, independent) sync service should build against for pulling an epic's full task/sub-task tree.

**Primary sources used**: this repo's own working Jira integration code (`packages/backend/src/services/jiraClient.ts`, `ticketSync.ts`, `sprintSync.ts`, `statusSync.ts`), its recorded live-verification results (`packages/backend/README.md`), the prior desk-research doc for this same integration (`.scratch/sprint-jira-integration/research/jira-api-integration-surface.md`), and official Atlassian docs (`developer.atlassian.com`, `support.atlassian.com`) fetched directly.

**A note on method**: I could not make new live calls against the real `wealthos.atlassian.net` instance for this ticket — this research ran in an isolated git worktree that has no `packages/backend/.env` (the file is gitignored and per-checkout, so it doesn't exist outside the main checkout), and I did not copy credentials into the worktree to make one appear. I wrote and then deleted a throwaway verification script (modeled on `src/scripts/verifyJira.ts`, GET/search-only) but it failed on a missing `JIRA_BASE_URL` for that reason, so it made zero live requests. Everything below instead comes from (a) this repo's already-live-verified code and its recorded findings (`ticketSync.ts` and `README.md`'s "Recorded results" section, both dated live confirmations against real WOSMVP issues), and (b) fresh reads of official Atlassian documentation. Anywhere this leaves an open question, it's flagged explicitly as "needs live verification" rather than guessed.

## 1. Which endpoint/JQL fetches an epic's tree — and which fits this app

**This app is on Jira Cloud, not Server/Data Center.** `jiraClient.ts` targets `/rest/agile/1.0` and `/rest/api/3` — the `/3` API generation only exists on Cloud (Server/DC tops out at `/2`) — and auth is Basic auth with an email + API token (`getConfig`/`authHeader`, `packages/backend/src/services/jiraClient.ts:74-92`), which is Cloud's auth model (Server/DC uses PATs or session cookies instead). `packages/backend/README.md` confirms live calls against `wealthos.atlassian.net`, a `*.atlassian.net` domain — Cloud.

**Recommendation: JQL via `POST /rest/api/3/search/jql`, not the Agile API's `/epic/{epicIdOrKey}/issue`.**

- The Agile API endpoint's own docs state: *"If you are querying a next-gen project, do not use this operation."* — [`api-group-epic`](https://developer.atlassian.com/cloud/jira/software/rest/api-group-epic/#api-rest-agile-1-0-epic-epicidorkey-issue-get). It's scoped to classic/company-managed projects only, uses old `startAt`/`maxResults` offset pagination, and is a second, narrower API surface this codebase doesn't otherwise touch for issue-level data (it's only ever used here for boards/sprints — `resolveBoard`, `listSprints`, `getSprint`, `getBoardConfiguration` in `jiraClient.ts:139-188`). Betting Atlas's core tree-fetch on an endpoint documented as unsafe for one of the two Jira project types is the wrong default when a project-type-agnostic alternative exists.
- The unified **`parent` field model has been fully rolled out since Feb 2024** across both company-managed and team-managed projects (per the existing repo research doc's citation of Atlassian's own rollout announcement — `.scratch/sprint-jira-integration/research/jira-api-integration-surface.md:162-169`), and this repo's `ticketSync.ts` already reads `fields.parent` as *the* epic/parent signal in production (`mapIssueToTicketFields`, `packages/backend/src/services/ticketSync.ts:73-100`) — confirmed live against real WOSMVP issues (`README.md`'s Aug 10 2026 recorded results: `fields.parent` populated on both a real sub-task-of-story and a real story-of-epic). JQL built on `parent`/`parentEpic` rides that same unified model and works regardless of project type, so it doesn't require Atlas to first determine (and keep tracking) whether the epic key it's given lives in a classic or team-managed project.
- `search/jql` is the only non-deprecated JQL search surface left: the old `/rest/api/3/search` is explicitly marked `"deprecated": true` in Jira's own OpenAPI spec and has been returning HTTP 410 in production since 2025 (`.scratch/sprint-jira-integration/research/jira-api-integration-surface.md:233-237`) — not viable for a brand-new integration.

**Concretely, two JQL options, both classic-vs-team-managed-agnostic:**

1. **Two-step, mirrors this repo's existing pattern exactly**: `parent = "<epicKey>"` to get direct children (level 0: Task/Story), then for each of those keys, `parent = "<childKey>"` to get its sub-tasks (level -1) — or bulk-fetch by the `fields.subtasks[].key` refs already present on each level-0 issue, which is literally what `ticketSync.ts`'s `fullSyncTickets` already does today (`packages/backend/src/services/ticketSync.ts:141-185`: bulk-fetch known keys, collect every returned issue's `fields.subtasks[].key`, bulk-fetch those in a second round trip). Atlas doing the epic-tree equivalent — JQL `parent = <epicKey>` for level 0, then bulk-fetch (or a second `parent =` JQL) for level -1 — is a near copy-paste of an already-proven, already-live-tested code path.
2. **One-shot, fewer round trips**: JQL's `parentEpic = "<epicKey>"` operator, which per Atlassian's own support KB "[will return an Epic's child work items **and** nested sub-tasks of those directly linked child work items](https://support.atlassian.com/jira/kb/retrieve-all-child-and-linked-work-items-of-an-epic-in-jira-cloud/)" in a single query — no manual recursion needed, since (per §2 below) the tree is only ever two levels deep below the epic anyway. This is worth prototyping for Atlas specifically because it's a flatter shape than `ticketSync.ts`'s two-round-trip pattern, at the cost of losing the parent/child linkage info in the single flat result set (would need `fields.parent`/`fields.subtasks` on each returned issue to reconstruct the tree structure — which `search/jql`'s `fields` param can request directly, so this is a non-issue in practice).

Either way, the request goes through `POST /rest/api/3/search/jql` with token-based pagination (§4) — this repo's `searchJql` (`jiraClient.ts:209-225`) already implements exactly that and can likely be reused as-is or with a small `fields` tweak; see §4.

**Needs live verification** (Atlas implementation time, not resolvable from a worktree with no Jira credentials): confirm `parentEpic = <epicKey>` actually returns the expected two-level set against a real WOSMVP epic (e.g. `WOSMVP-8262`, a real epic already confirmed live per `ticketSync.ts`'s own comments), and compare its result set against the two-step `parent =` approach to sanity-check they agree before committing to the one-shot query in Atlas's sync service.

## 2. How many hierarchy levels exist below Epic

**Sub-task is a hard floor — Epic → Task/Story → Sub-task is the full depth, no exceptions found in official docs, and it's already this codebase's working assumption.**

- Atlassian's own admin docs: *"Jira has three default levels of work type hierarchy: a level for larger pieces of work (level 1, called Epic), a level for standard work items (level 0, called Story), and a level for smaller pieces of work (level -1, called Subtask)."* — [Configure the work type hierarchy](https://support.atlassian.com/jira-cloud-administration/docs/configure-the-issue-type-hierarchy/). No level below -1 is documented anywhere.
- Extra hierarchy levels are a real, paid Jira feature (**Advanced Roadmaps**, Premium/Enterprise only) — but they only ever add levels **above** Epic (level 2+, for things like "Initiative"), never below Sub-task: *"Jira Premium and Enterprise customers can also create and manage additional levels in their work type hierarchy"* (same page) — [Configure custom hierarchy levels in your plan](https://support.atlassian.com/jira-software-cloud/docs/configure-custom-hierarchy-levels-in-advanced-roadmaps/) confirms these are added on top, not underneath. So even on an instance with custom hierarchy levels enabled, Sub-task's floor position doesn't move.
- This matches how the existing app's own sync code is already written: `ticketSync.ts`'s `fullSyncTickets` does exactly **one level of subtask-following** (`primaryResult.issues` → collect `fields.subtasks[].key` → one more `bulkFetchIssues` call, `packages/backend/src/services/ticketSync.ts:146-156`) and never recurses further — because there's nothing further to recurse into. The `isEpicParent` distinction (`ticketSync.ts:75`) also assumes exactly two possible parent kinds for any issue's `fields.parent`: an Epic, or a non-Epic (Story/Task) — consistent with a fixed 3-level ceiling.
- The map's own domain decision ("Sub-task depth: full treatment, same shape as Task, recursive" — `.scratch/sprint-atlas-program/map.md`) describes Atlas's *data model* as recursive (Task and Sub-task share one shape, nested one level deeper), but that's a modeling choice, not evidence Jira itself goes deeper — Jira-side, the recursion bottoms out after exactly one hop past the epic's direct children. Atlas's sync only ever needs to walk two levels (epic → children → grandchildren-that-are-subtasks), never more.

**Needs live verification**: none really — this is Jira Cloud platform-level, instance-independent behavior (not a WOSMVP-specific fact), and it's corroborated by this repo's own already-live-tested code making exactly this assumption. Worth only a defensive sanity check in Atlas's sync (e.g. log a warning, don't crash, if a fetched "sub-task" ever unexpectedly carries its own non-empty `subtasks` array) rather than a dedicated verification pass.

## 3. Which fields carry status category, assignee, and start/due dates

**Status category** — `fields.status.statusCategory`, an object shaped `{id, key, name, colorName}`, confirmed structurally via Atlassian's own [Jira expressions type reference](https://developer.atlassian.com/cloud/jira/platform/jira-expressions-type-reference/#statuscategory). The `key` is the stable "which bucket" signal Atlas wants for its To Do/In Progress/Done collapse — Jira's three category keys are `new` (To Do bucket), `indeterminate` (In Progress bucket), and `done` (Done bucket). This is a cleaner source than `statusSync.ts`'s current approach: that file infers category from a board column's *position* (first/last/middle — `packages/backend/src/services/statusSync.ts:16-20`) because the board-configuration endpoint it reads doesn't carry category info at all. Atlas isn't board-scoped the way Sprint/Status is (it works off arbitrary epic keys, no board lookup), so it should read `fields.status.statusCategory.key` directly off each synced issue instead of reimplementing a column-position heuristic — a strictly better signal that happens to be available specifically because Atlas's data shape doesn't need `statusSync.ts`'s board-configuration detour at all.

**Assignee** — `fields.assignee`, a `User` object (`{accountId, displayName, emailAddress, ...}`), already used by this codebase's `mapIssueToTicketFields` (`ticketSync.ts:70,93-95`). Per the existing research doc's citation of Atlassian's [User privacy developer guide](https://developer.atlassian.com/cloud/jira/platform/user-privacy-developer-guide/), `emailAddress` and `displayName` can be `null` depending on the assignee's account privacy settings — `accountId` is the only field guaranteed present for an active assignee, so Atlas should key off `accountId` the same way `Ticket.assigneeAccountId` already does, not `emailAddress`.

**Due date** — `fields.duedate`, a standard Jira **system** field (not custom), date-only (no time component) — confirmed via Atlassian's [Add the due date field to your work items](https://support.atlassian.com/jira-software-cloud/docs/add-the-due-date-field-to-your-issues/), which also notes it must be explicitly present in the project's field configuration (company-managed: once per project; team-managed: "the due date needs to be configured for each work type") to be *settable through the Jira UI* — but as a system field it's still a normal readable key on `fields` via the API regardless of UI visibility (same category as `labels`, already used elsewhere in this codebase without any such caveat).

**Start date** — **no standard system field exists.** Every official source checked (the due-date doc above, and general search of Atlassian's JQL fields docs) discusses "Start date" only in the context of either a project-specific custom field an admin adds, or the Premium/Enterprise **Advanced Roadmaps/Timeline** feature's own start-date tracking — never as a system field alongside `duedate`. If Atlas ever wanted a Jira-sourced start date (it currently doesn't — the map's decision is "Dates: manual, set in Atlas — not pulled from Jira"), it would need the same `field/search?query=<name>&type=custom` discovery dance `ticketSync.ts` already does for the "Stream" field (`STREAM_FIELD_ID`, `ticketSync.ts:10`), not a fixed field id assumable in advance.

**Needs live verification**: whether WOSMVP's Task/Story/Sub-task issue types actually have `duedate` populated on any real issues (the field being a valid API key doesn't mean anyone fills it in) — purely informational per the ticket's own framing, doesn't block Atlas's design since dates are manual there regardless.

## 4. Pagination and rate-limit handling to reuse

`jiraClient.ts` already has two working, different pagination shapes worth copying directly rather than reinventing for Atlas:

- **Token pagination** (`searchJql`, `jiraClient.ts:209-225`): loops on `nextPageToken` from `POST /rest/api/3/search/jql`, no upper page-count guard (the API's own token contract terminates the loop — no token in the response means last page). This is the shape for any new JQL-based epic-tree fetch Atlas adds — the endpoint recommended in §1.
- **Offset pagination with a runaway-loop guard** (`listSprints`, `jiraClient.ts:156-174`): loops on `startAt`/`isLast` against the Agile API's `startAt`/`maxResults` style, capped at `MAX_SPRINT_PAGES = 20` purely as a guard against a malformed `isLast`, documented as "not an expected ceiling" (`jiraClient.ts:146-154`). Only relevant to Atlas if it ever calls the Agile API directly (§1 recommends against that for the tree-fetch itself, but Atlas might still resolve a board via `resolveBoard` for other reasons) — otherwise this shape doesn't apply.
- **Chunked bulk fetch** (`bulkFetchIssues`, `jiraClient.ts:190-207`): splits any key list into `BULK_FETCH_CHUNK_SIZE = 100`-key batches against `POST /rest/api/3/issue/bulkfetch` (Jira's own documented ceiling per issue/bulkfetch — [`api-group-issue-search`](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/#api-rest-api-3-issue-bulkfetch-post): *"You can request up to 100 issues."*). Directly reusable for Atlas's "hydrate N known child/grandchild keys" step, exactly as `ticketSync.ts:145,154,175` already uses it three separate times in one sync pass (primary keys, subtask keys, epic keys).
- **Rate-limit / 429 handling** (`jiraFetch`, `jiraClient.ts:98-115`): a single retry after respecting the server's `Retry-After` header, deliberately not a backoff loop — the code comment justifies this against Jira Cloud's documented points-based hourly quota (tens/hundreds of thousands of points per hour vs. a manual sync costing on the order of 30-100 points, per the existing research doc's citation of [Rate limiting](https://developer.atlassian.com/cloud/jira/platform/rate-limiting/), `.scratch/sprint-jira-integration/research/jira-api-integration-surface.md:289-311`). Atlas's own sync (manually triggered by entering an epic key, same "occasional click" usage shape as the existing Sprint/Status sync buttons) fits the same justification with no changes needed — this is infrastructure-level, not Sprint-specific, so it's a strong candidate to reuse `jiraFetch`/`jiraJson` (or `jiraClient.ts` wholesale) rather than reimplementing auth/retry logic in a second client.

**Design implication for Atlas**: since none of `jiraClient.ts`'s exported functions are Sprint/Ticket-model-specific (they return raw `JiraIssue`/`JiraSprint`/etc., not this app's Mongoose docs — the model-shaping happens entirely in `ticketSync.ts`/`sprintSync.ts`, one layer up), Atlas's own sync service can likely **import `jiraClient.ts` directly** (`searchJql`, `bulkFetchIssues`, maybe `resolveBoard` if ever needed) rather than duplicating a second Jira HTTP client — the map's "not yet specified" item about whether Atlas reuses the existing Jira client now has a concrete answer: yes, at the `jiraClient.ts` layer (auth/pagination/rate-limiting), while writing its own new `atlasSync.ts`-equivalent mapping layer (parallel to `ticketSync.ts`) that targets Atlas's brand-new Mongo collections instead of `Ticket`/`Epic`.
