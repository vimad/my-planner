# 02 — "Add from backlog" popover UI

**What to build:** The "Add from backlog" button, anchored popover, and avatar treatment in Sprint Planning, backed by the real endpoint from ticket 01. Picking a backlog ticket reuses the existing add-by-key pipeline and the existing per-ticket detail popups verbatim — no new popup, no new mutation route. See `.scratch/add-from-backlog/spec.md` for full context, including the winning layout prototype preserved on branch `prototype/add-from-backlog-ui` (commit `ee6fac5`, Variant A).

**Blocked by:** 01 — Backlog browse endpoint.

**Status:** ready-for-agent

- [ ] New `components/Avatar.tsx`: round initials avatar (first-of-its-kind in this app). Two initials from the first two words of a name (e.g. "Vinod Madubashan" → "VM"); background color deterministically hashed from the name into a small curated palette (own palette, distinct from `constants/categoryColors.ts`). `null`/unassigned always renders "UN" on a neutral slate background, never a palette color. Scoped to this feature only — do not retrofit other existing plain-text person displays elsewhere in the app.
- [ ] New `components/AddFromBacklogPopover.tsx`: Archetype A anchored popover (`docs/ui-conventions.md`), same shape/positioning convention as `AddSprintPopover.tsx` (trigger button + `absolute`-positioned panel below it, closes on outside click). Contents: category tab row (Technical/Product/Bugs), a search input that filters the already-fetched category client-side by key/title, a scrollable result list (ticket key, truncated title, avatar(s) — Dev+QA for Story/Bug, one assignee avatar for Task), and loading/error states per fetch.
- [ ] Popover fetches the active category from `GET /api/tickets/backlog` when it opens and whenever the active tab changes (not all three categories upfront) — mirrors `AddSprintPopover`'s existing "don't call Jira until there's something to show" convention.
- [ ] `hooks/useSprintPlan.ts`: add `fetchBacklog(category, query)` wrapping the new endpoint, and `addFromBacklog(jiraKey)` that calls the existing `addTicket(jiraKey)` internally, then — as a separate pending-open code path alongside the existing `pendingAutoOpenTicketId` one — **always** opens the popup (`popupTicketId`) once the new entry reappears in `entries`, regardless of resolved/needs-assignment/unmapped status. The existing typed "Add" button's conditional (needs-assignment-only) auto-open behavior is unchanged.
- [ ] `components/PlanningView.tsx`: new icon-only button (suggest lucide `Inbox`, matching the existing icon-only-button hover convention) in `AddToPlanForm`, immediately after "Add placeholder ticket", mounting `AddFromBacklogPopover`. Picking a result closes the popover and lands on the real `DevQaAssignmentPopup` (Split ticket) or `TicketInfoPopup` (Task) — unmodified, reused exactly as they already render for an in-plan ticket — pre-filled from Jira's current Dev/QA/assignee.
- [ ] Confirm (manually, against real Jira per `CLAUDE.md`'s read-only workflow) that closing the popup without saving leaves the picked ticket as a bare/unassigned entry in "Tickets by person", identical to today's typed-Add behavior — no special-casing.
- [ ] Frontend tests:
  - `components/Avatar.test.tsx` (new): initials extraction (two-word name, one-word name, `null` → "UN"); color assignment is deterministic per name; `null` always renders the neutral/slate treatment, never a palette color.
  - `components/AddFromBacklogPopover.test.tsx` (new, modeled on `AddSprintPopover.test.tsx`'s live-fetch-popover pattern): opening fetches the default category; switching tabs re-fetches; typing in search narrows the rendered list without an extra fetch; loading/error states render; clicking a result closes the popover and invokes the pick callback with that ticket's key.
  - `hooks/useSprintPlan.test.ts` (existing file, extend): `addFromBacklog` calls `addTicket` then always opens the popup once the entry appears in `entries`; a regression case confirms the existing typed-Add path's conditional (needs-assignment-only) auto-open is untouched.
  - No new assertions needed in `DevQaAssignmentPopup.test.tsx`/`TicketInfoPopup.test.tsx` — both are reused unmodified, existing coverage stands.
